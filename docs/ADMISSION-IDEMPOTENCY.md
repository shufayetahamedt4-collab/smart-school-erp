# Admission intake is idempotent (pilot P2b)

One submit at the desk is one admission. The form mints ONE key per submit attempt and keeps it while that attempt is unfinished — pressing *Admit* again can only replay what the first call recorded — minting a new key only for a new admission. The route takes the key from the body or `x-idempotency-key`, and refuses one that is present but unusable (8–120 chars) by name, because silently ignoring a key would quietly turn a once-only admission into a repeatable one.

With a key, the admission row's id is `adm_sha1(schoolId|key)`, so the row IS the attempt, and it is created inside a real Firestore transaction (`$guardedUpdate`): the winner inserts, the loser is handed the winner's row. The admission fee is paid through the existing keyed `confirmPayment` with a key derived from the intake key (`<key>:admission-fee`), and only the key's HASH is stored on the row.

A replay — sequential, a second tab, or the loser of a simultaneous pair — is answered from that record before any pricing, phone+name guard or kit work: **200**, `replay: true`, the ORIGINAL admission id, student, receipt and the same QR token/PIN, and it writes nothing (no second admission, student, fee row, payment, ledger entry, kit issue or notification). A keyed attempt whose row exists but never linked a student (the process died) is refused **409**, naming that admission and its state, instead of being re-run.

Not covered: a *different* key for the same child. That still rests on the old pre-read guard (guardian phone + name), which two truly simultaneous submits with different keys can both pass, and which does nothing when the phone is empty — the honest residue is "two different keys, same child, at the same instant" (measured in `proof/p2b/REPORT.md`). The existing guard is left exactly as it was. Keyless callers are unchanged: no key means the previous create, response shape included, which is why `verify-admission-intake` (52) still passes untouched.
